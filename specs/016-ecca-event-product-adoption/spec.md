Doing both surfaced real correctness gaps in the already-published `traverse-registry` 0.10.0 API, not cosmetic ones:

- **No exposure class**: Spec 534 FR-007 requires a top-level exposure class (`public`/`partner`/`internal`/`restricted`) on every event, separate from field-level classification. v1.0.0 had no such field.
- **Wrong field-classification vocabulary**: FR-007 requires per-field values `none`/`personal`/`sensitive`/`regulated`. v1.0.0 shipped an invented `public`/`internal`/`confidential`/`restricted` taxonomy that satisfies no governing document.
- **Naming-grammar check diverges from Traverse's own runtime validator**: Traverse's `is_fact_type` checks whether the last dot-segment of the fully-qualified event type ends in `-ed` -- no irregular-verb allowance. v1.0.0 checked the last *hyphen*-segment of the kebab-case `name` field plus a curated irregular-participle allow-list Traverse's side does not have, meaning v1.0.0 could accept a name (e.g. one ending `-sent`) that Traverse's own runtime would reject.
- **Missing CloudEvents envelope mapping**: FR-005 requires the descriptor to declare `source`/`subject`/`time` mapping, not just `type`. v1.0.0 only asserted `EventContract.id` serves as `type` and stopped there.
- **Missing delivery-semantics declarations**: FR-010 (deduplication identity, ordering scope, correlation ID, causation ID) sits in Spec 534's *descriptor* requirements section, not a runtime-only section. v1.0.0 scoped this out entirely as "stays in Traverse" -- that was the wrong scoping call; the descriptor must *declare* these, even though enforcing them at delivery time stays in Traverse.
- **Validation diagnostics missing required fields**: FR-012 requires `remediation`, `contract_id`, `version`, and a governing-spec reference on every diagnostic. Traverse's own `EventValidationDiagnostic` already carries all of these. v1.0.0's `EventProductValidationError` only had `code`/`path`/`message`/`severity`.

This amendment corrects all six. No fix changes an already-*correct* v1.0.0 requirement -- every changed FR below is either a genuinely new requirement or a vocabulary/algorithm correction. ## Why This Is An Adoption, Not A Fresh Spec

`Spec 534`/`ADR-0028` are already owner-authored and Accepted in `traverse-framework/traverse`. This spec does not re-litigate their decisions; it translates the subset that is registry behavior (governed event-product descriptors, publish-time validation, declared-vs-observed lineage, catalog/discovery) into this repo's own spec-numbered governance, the same way `011`/`012` translated `traverse`'s `005`/`011-event-registry`. It does not cover the parts of `ADR-0028`/Spec 534 that are runtime/transport/wire-protocol/enforcement concerns (CloudEvents delivery, OpenTelemetry evidence collection, quarantine enforcement, enforcement-mode cutover) -- those stay in `traverse`, out of this spec's scope, per the existing registry/runtime boundary (`013`'s own scope note). The descriptor must *declare* delivery-semantics and envelope-mapping metadata (Spec 534 FR-005/FR-010); actually delivering, enforcing, or observing them at runtime remains Traverse's.

## Purpose

This spec defines the ECCA event-product slice for `traverse-registry`, layered on top of the existing `012-event-registry-adoption` event registry rather than replacing it. `traverse-contracts` (the crate that defines `EventContract`) is an exact-pinned external dependency (`= "0.8.1"`, published from `traverse-framework/traverse`); this repo cannot add fields to `EventContract` itself. Every requirement below is additive: a registry-owned `EventProductDescriptor` that composes around an already-validated `EventContract`.

This spec covers:

- the canonical ECCA event-product descriptor: an `EventProductDescriptor` wrapping a `012`-validated `EventContract` plus ECCA-additive fields (stable support route, exposure class, controlled field-level classification, lifecycle-deprecation replacement pointer, CloudEvents source/subject mapping, delivery-semantics field declarations, retention policy)
- publish-time validation that rejects a descriptor when any ECCA-additive field, or the semantic (past-tense) naming rule, is absent or invalid
- immutable republication semantics for a descriptor at a given `(scope, id, version)`, consistent with `012`'s immutability model for the underlying contract
- persisted, indexed storage of declared producer/consumer relationships (already partially satisfied by `012`'s `EventRegistry.publishers`/`subscribers` -- this spec extends indexing/discovery, not the underlying storage)
- a registry-owned, structurally separate record of **observed** runtime lineage and drift evidence, isolated from declared/governed state (mirroring `015-runtime-usage-telemetry-resolve-hook`'s external, side-effect-only, "MUST NOT affect the declared path" hook shape)
- a catalog/discovery query surface exposing event contract/version/schema/purpose, owner/support route, lifecycle, exposure/field classification, compatibility, publishers/consumers, and declared-vs-observed lineage, filterable by event, capability, domain, owner, lifecycle, and classification
- AsyncAPI as a derived export of the above, never a source of truth
- deterministic validation diagnostics carrying remediation guidance, contract identity, and a governing-spec reference

This spec does **not** cover:

- CloudEvents wire-format delivery, transport, or broker behavior (stays in `traverse`)
- OpenTelemetry evidence collection, runtime enforcement, or quarantine (stays in `traverse`; this repo only stores the resulting evidence records once produced)
- changes to `traverse-contracts`' `EventContract` type itself (out of this repo's control; exact-pinned external dependency)
- the Traverse runtime/reference-app conformance journey (`traverse#897`/`traverse#898`)
- FR-020-equivalent capability-inventory/migration work for this repo's own published `capabilities/` tree (tracked separately, see `traverse-framework/registry#170`)

## Scope

In scope: `crates/traverse-registry/` (new modules), and this spec's own directory.

Out of scope: `traverse-contracts`, `traverse-runtime`, `traverse-cli` (all stay in `traverse`, per the existing registry/runtime boundary already established by `013`).

## Requirements

### Functional Requirements

- **FR-001**: The registry MUST define an `EventProductDescriptor` that composes an already-`012`-validated `EventContract` with ECCA-additive metadata, without modifying `EventContract` itself.
- **FR-002**: Descriptor validation MUST reject a descriptor with a missing or non-`https://` support route. This route is scoped narrowly by `NFR-007`: it is not a general "ask a question" channel, and it is not where routine compatibility questions belong -- those are answered by the descriptor's own governed metadata (version, schema, compatibility, `replacement`). It exists for the residual a contract cannot structurally cover.
- **FR-003**: Descriptor validation MUST reject a descriptor whose field classifications do not exactly cover the top-level properties declared in the underlying contract's `payload.schema` (each declared property classified exactly once; no classification for an undeclared property), using the exact vocabulary Spec 534 FR-007 requires: `none`, `personal`, `sensitive`, `regulated`.
- **FR-004**: Every descriptor MUST declare exactly one exposure class (Spec 534 FR-007): `public`, `partner`, `internal`, or `restricted`. This is a Rust enum, not a free-form string -- an invalid value is unrepresentable, satisfying "exactly one" and "free-form class names are invalid" by construction.
- **FR-005**: Descriptor validation MUST require a replacement pointer when the underlying contract's lifecycle is `deprecated` or `retired`, and MUST reject a replacement pointer when lifecycle is `draft` or `active`. (Note: `traverse-contracts::Lifecycle` uses `active`, not Spec 534's `approved` -- an unresolvable naming mismatch against an external, exact-pinned dependency this repo cannot rename; `active` is treated as the equivalent of Spec 534's `approved` throughout this spec. `traverse-contracts::Lifecycle` also has a fifth state, `archived`, that Spec 534 does not define; this spec treats `archived` the same as `retired` for replacement-pointer purposes, since neither permits new registration.)
- **FR-006**: Descriptor validation MUST reject a replacement pointer with an empty `event_id`/`version`, or one that is self-referential (points at the same `(id, version)` being validated).
- **FR-007**: Descriptor validation MUST reject a contract `name` that does not end with `ed` -- matching Spec 534 FR-004's past-tense fact grammar exactly as Traverse's own `crates/traverse-runtime/src/events/validation.rs::is_fact_type` implements it (whole-name suffix check, no irregular-verb allow-list). This deliberately narrows v1.0.0's more lenient irregular-participle allowance to stay consistent with the runtime side actually enforcing it.
- **FR-008**: Every descriptor MUST declare a CloudEvents-compatible `source` (a non-empty string) and MAY declare a `subject` field reference, which MUST name a property actually declared in the underlying contract's `payload.schema` when present (Spec 534 FR-005). `type` continues to be satisfied by the existing, already-validated `EventContract.id` (spec 012); `time` is a runtime-populated envelope value, not a descriptor-declared one, and stays out of scope here.
- **FR-009**: Every descriptor MUST declare a deduplication-identity reference and a correlation-identity reference (both non-empty strings) and MAY declare an ordering-scope reference and a causation-identity reference (Spec 534 FR-010). These are descriptor-level *declarations* of which field or envelope concept serves each role -- enforcing them at delivery time, and the at-least-once delivery guarantee itself, remain Traverse's runtime responsibility, not this repo's.
- **FR-010**: Every descriptor MUST declare a non-empty retention policy statement (Spec 534 FR-005's "retention/deprecation information" -- deprecation itself is FR-005/FR-006 above; this FR covers the retention half).
- **FR-011**: A previously published descriptor for the same `(scope, id, version)` MUST be immutable; validating a candidate descriptor against an existing one with different content MUST fail, and against identical content MUST succeed idempotently.
- **FR-012**: Declared producer/consumer relationships MUST remain sourced from the underlying `EventContract`'s `publishers`/`subscribers` (already governed by `012`) -- this spec MUST NOT introduce a second, divergent declared-relationship model.
- **FR-013**: Observed runtime lineage and drift evidence MUST be stored in a structure disjoint from declared/governed descriptor state, MUST be supplied only by an external, side-effect-only caller (mirroring `015`'s hook isolation), and MUST NOT be inferable from, or influence, descriptor validation.
- **FR-014**: The registry MUST expose a catalog/discovery query surface over event contract/version/schema/purpose, owner/support route, lifecycle, exposure/field classification, compatibility, publishers/consumers, and declared-vs-observed lineage, filterable by event, capability, domain, owner, lifecycle, and classification.
- **FR-015**: Any AsyncAPI representation the registry produces MUST be generated from the governed descriptor and MUST NOT be hand-authored or treated as contract authority.
- **FR-016**: Descriptor validation and catalog discovery results MUST be deterministic for identical stored records and query inputs, consistent with `012`'s `NFR-001`.
- **FR-017**: Every validation diagnostic MUST carry, in addition to its error code/path/severity: a human-actionable remediation string, the contract's `id`, the contract's `version`, and a reference to this spec as the governing spec (Spec 534 FR-012).

### Non-Functional Requirements

- **NFR-001 Determinism**: Descriptor validation, immutability checks, and catalog discovery MUST be deterministic for identical inputs.
- **NFR-002 Explainability**: Validation failures MUST produce stable, machine-readable evidence with an error code, path, message, remediation, contract identity, and governing-spec reference (FR-017), consistent with `012`'s `EventRegistryError` shape and Traverse's own `EventValidationDiagnostic` shape.
- **NFR-003 Isolation**: Observed-lineage/drift-evidence recording MUST be structurally isolated from declared-state validation and storage; a failure or absence of observed data MUST NOT change declared-state validation outcomes.
- **NFR-004 Testability**: Core validation and catalog-discovery logic MUST be structured for full automated coverage, independent of any WASM/host-runtime dependency.
- **NFR-005 Non-duplication**: This spec MUST reuse `012`'s existing `EventContract`/`EventRegistry` validation and storage wherever it already satisfies an ECCA requirement, rather than re-implementing it.
- **NFR-006 Cross-repo consistency**: Wherever Traverse's own runtime code (`crates/traverse-runtime/src/events/validation.rs`) already implements a Spec-534-governed check this repo also implements, this repo's check MUST produce the same accept/reject outcome for the same logical input -- registry MUST NOT be more lenient than the runtime boundary it feeds.
- **NFR-007 Self-service, no human bottleneck**: Every routine question a consumer has about a governed event product -- is this version still valid, what changed between versions, where is the replacement for a deprecated version, what does a capability declare it publishes or consumes -- MUST be answerable entirely from the governed descriptor and this crate's deterministic APIs (`validate_event_product_descriptor`, `EventProductRegistry::discover`/`catalog_search`/`declared_publishes`/`declared_consumes`), with no human interaction required. A support-route interaction (FR-002) is reserved for what a governed contract cannot structurally resolve: semantic drift not expressible in a schema, declared-vs-observed lineage drift once actually observed, and genuine incidents in emitted data -- never for a question the descriptor itself already answers. This is a design constraint on every future FR added under this spec, not only on `FR-002`: new capability MUST default to self-service, and any human-in-the-loop step MUST be justified as covering something the contract structurally cannot.

## Success Criteria

- **SC-001**: A valid event-product descriptor can be validated and accepted; an invalid one is rejected with a specific, addressable error for each violated rule.
- **SC-002**: Republishing an unchanged descriptor for the same `(scope, id, version)` is idempotent; republishing changed content for the same `(scope, id, version)` is rejected.
- **SC-003**: Declared and observed relationship data remain structurally distinguishable at all times -- no code path can produce declared-state output from observed-state input or vice versa.
- **SC-004**: `traverse#896`'s catalog/discovery DoD items are each traceable to one or more FRs above.
- **SC-005**: Every field-classification and exposure-class value this crate accepts or emits matches Spec 534 FR-007's exact vocabulary, verifiable by fixture comparison against `traverse-framework/traverse`'s own `contracts/governance/` conventions.
- **SC-006**: A name that Traverse's own `is_fact_type` would reject is also rejected here, and vice versa, for the same input string (NFR-006).
- **SC-007**: A consumer can determine version validity, what changed, and a deprecated version's replacement using only the descriptor and this crate's query APIs -- no fixture, test, or real usage ever needs a human-in-the-loop step to answer one of those three questions (NFR-007).

## Governing Relationship

This specification is adopted from `traverse-framework/traverse`'s `Spec 534`/`ADR-0028`, and governs `crates/traverse-registry/` in this repo for ECCA event-product behavior, layered additively on `011-capability-registry-adoption`, `012-event-registry-adoption`, and `013-inherited-registry-governance`.
